# Алгоритм работы СМО

## Заявка и параметры

Заявка содержит requestId, sourceId, imageUri и arrivalAt. Она представляет задание на создание миниатюры 800×800 WebP. Прибор IMG-i выполняет декодирование, масштабирование и кодирование изображения. В модели длительность этой работы задаётся случайной величиной τ, результат обозначается ссылкой resultUri.

Входные параметры: число источников N ≥ 1, число приборов M ≥ 1, вместимость буфера B ≥ 1, интенсивности λi > 0, границы времени обслуживания 0 < tmin ≤ tmax и число генерируемых заявок requestLimit ≥ 1. Единица времени — секунда. Начальное состояние: t = 0, приборы свободны, буфер пуст, указатель p = 0, счётчики равны нулю. Ячейки нумеруются от 0 до B−1, источники и приборы — от 1.

По ИЗ1 каждый источник формирует независимый пуассоновский поток. Интервал до следующей заявки Δt = −ln(U)/λi, U ∈ (0;1). По ПЗ2 время обслуживания τ = tmin + U·(tmax−tmin). Среднее время обслуживания равно (tmin+tmax)/2. Каждому источнику и прибору соответствует отдельный поток случайных чисел с начальным состоянием, зависящим от общего seed.

## Календарь событий

При инициализации для каждого источника планируется первое поступление. Занятый прибор имеет в календаре событие завершения обслуживания. Ближайшее событие выбирается по ключу (time, kindPriority, targetId). При одинаковом времени сначала обрабатываются завершения, затем поступления; внутри типа события — по возрастанию номера прибора или источника.

Один step() обрабатывает событие календаря и вызванные им действия диспетчеров. Постановка в буфер, вытеснение, выборка и начало обслуживания записываются в журнал с тем же модельным временем. Перед изменением состояния Statistics.advanceTo() учитывает занятость приборов и длину очереди за прошедший интервал.

После генерации последней заявки новые поступления удаляются из календаря. Обслуживание продолжается до освобождения всех приборов и опустошения буфера. Полное время реализации T равно моменту завершения последней заявки.

## Поступление заявки

1. Источник создаёт заявку. Модель назначает ей общий возрастающий requestId, учитывает поступление и увеличивает generated. Пока generated < requestLimit, источник планирует следующее поступление по ИЗ1.
2. Модель вызывает AdmissionDispatcher.accept(q, t). Диспетчер постановки запрашивает свободный прибор через SelectionDispatcher.findFreeDevice().
3. По Д2П1 DevicePool.firstFree() проверяет приборы от IMG-1 до IMG-M. Если свободный прибор найден, startOn() передаёт ему заявку и планирует завершение в момент t+τ. Время ожидания равно нулю. Буфер и p не меняются.
4. Если все приборы заняты, диспетчер постановки вызывает RingBuffer.offer(q). По Д10З1 проверяется не более B ячеек, начиная с p. После ячейки B−1 проверяется ячейка 0.
5. В первую найденную свободную ячейку k записывается q. Указатель устанавливается в p = (k+1) mod B.
6. Если свободных ячеек нет, полный обход возвращает указатель в исходную позицию. По Д10О1 из slots[p] удаляется старая заявка, а её место занимает новая. Затем p = (p+1) mod B.
7. OfferResult возвращает номер занятой ячейки и ссылку на вытесненную заявку либо null. Диспетчер учитывает отказ вытесненной заявки и уведомляет её источник кодом 503 OVERLOAD. Постановка новой заявки записывается в журнал.

Прибор продолжает текущую обработку независимо от переполнения буфера. Отказ получает только вытесненная ожидающая заявка.

## Завершение обслуживания

DevicePool.finish(deviceId, t) завершает обработку и освобождает прибор. Модель фиксирует результат, учитывает время пребывания заявки и уведомляет её источник. Затем вызывается SelectionDispatcher.dispatchWaiting(t).

Пока в буфере есть заявки и найден свободный прибор, диспетчер выбирает прибор с минимальным номером по Д2П1 и извлекает старейшую заявку по Д2Б1. FIFO определяется минимумом (arrivalAt, requestId) среди всех занятых ячеек. requestId разрешает равенство времени поступления. Освободившаяся ячейка остаётся пустой, другие заявки не сдвигаются, p не меняется.

Выбранная заявка сразу поступает на прибор. Учитывается начало обслуживания, в календарь добавляется завершение в момент t+τ. Если буфер пуст, прибор остаётся свободным. После каждого завершённого шага ожидающая заявка и свободный прибор не могут присутствовать одновременно. Поэтому при прямой передаче новой заявки свободному прибору буфер пуст.

## Граничные случаи

Обозначение q1(1) означает заявку q1 с arrivalAt = 1.

| Условие | Событие | Результат |
|---|---|---|
| Буфер пуст, IMG-1 и IMG-2 свободны | Поступает q | q поступает на IMG-1, буфер и p не меняются |
| Все приборы заняты; B=3, p=2, [пусто,q1,q2] | Поступает q3 | Проверка 2→0; [q3,q1,q2], p=1 |
| Все приборы заняты; B=3, p=0, [q2(2),q1(1),q3(3)] | Поступает q4(4) | Вытеснена q2; [q4,q1,q3], p=1; отказ учитывается источнику q2 |
| После предыдущего события освобождается прибор | Выборка FIFO | На прибор поступает q1; [q4,пусто,q3], p=1 |
| B=1, p=0, прибор и ячейка заняты | Поступает q2 | Старая заявка вытеснена, в ячейке q2, p=0 |
| Буфер пуст | Завершается обслуживание | Прибор остаётся свободным |
| В буфере две заявки с одинаковым arrivalAt | Освобождается прибор | Выбирается заявка с меньшим requestId |
| Одновременно завершается обработка и поступает q | Завершение, затем поступление | Сначала обслуживается очередь, затем принимается q |
| Достигнут requestLimit, есть заявки в системе | Завершение генерации | Новых поступлений нет; оставшиеся заявки дообслуживаются |

## Сбор статистики

Счётчики поступлений, отказов и завершений ведутся по каждому источнику. При отказе используется sourceId вытесненной заявки. При начале обслуживания сохраняются tStart и время ожидания tStart−arrivalAt. При завершении определяются время обслуживания tFinish−tStart и время пребывания tFinish−arrivalAt. Суммы времён ожидания и обслуживания и суммы их квадратов накапливаются по источникам для обслуженных заявок. Ожидание до отказа хранится отдельно.

Для источника i:

- nᵢ — число сгенерированных заявок;
- mᵢ — число отказов, cᵢ — число обслуженных заявок;
- pотк,i = mᵢ/nᵢ;
- TБП,i = Σ(tStart−arrivalAt)/cᵢ;
- Tобсл,i = Σ(tFinish−tStart)/cᵢ;
- Tпреб,i = TБП,i + Tобсл,i;
- ДБП,i = Σ(tStart−arrivalAt)²/cᵢ − TБП,i²;
- Добсл,i = Σ(tFinish−tStart)²/cᵢ − Tобсл,i².

При нулевом знаменателе соответствующий показатель не определён. Отказы не входят в средние времена обслуженных заявок. После дообслуживания nᵢ = mᵢ+cᵢ.

На каждом интервале Δt для занятого прибора увеличивается накопленное время занятости. Коэффициент использования Kисп,j = busyTimeⱼ/T. Средняя длина очереди равна площади под её длиной, делённой на T. После каждого события проверяется баланс Nпост = Nобсл + Nотк + Nбуфер + NнаПриборах.

Журнал содержит модельное время, действие, requestId, sourceId, номер ячейки или прибора и новое положение p. ОД1 показывает календарь событий, B ячеек буфера, p, состояния приборов, число заявок и текущие показатели. Итоговая таблица источников содержит nᵢ, pотк,i, Tпреб,i, TБП,i, Tобсл,i, ДБП,i и Добсл,i. Отдельная таблица содержит Kисп каждого прибора. По ОР2 строятся графики pотк, Tпреб и Kисп при изменении λΣ, M и B.

## Автоматический режим

Для оценки необходимого числа заявок выполняется предварительный запуск с L₀ = 100. По полученной вероятности отказа p определяется L₁ = max(L₀, ceil(1,643²·(1−p)/(p·0,1²))). Здесь относительная точность δ = 0,1, доверительная вероятность α = 0,9. После следующего запуска проверяется |p₁−p₀|/p₀; при изменении не менее 10% оценка числа заявок повторяется с увеличением числа заявок как минимум вдвое. Перед каждым новым запуском состояние системы и статистика сбрасываются.

При нулевом числе отказов формула не применяется: число заявок предварительного запуска удваивается. Нулевое эмпирическое значение не принимается за подтверждение требуемой относительной точности. Для серии опытов задаются диапазоны λΣ, M и B; каждому запуску соответствуют отдельные параметры и результаты.

## Буферная память

Используется общий буфер. Все заявки требуют одинакового преобразования и могут обслуживаться любым прибором. Свободные ячейки доступны каждому источнику, независимо от распределения нагрузки между загрузкой товаров, импортом и CMS.

Зонная память нужна для резервирования части буфера за источниками или группами клиентов. Например, отдельная зона для CMS ограничит влияние массового импорта на её заявки. При этом свободные ячейки чужой зоны могут оставаться недоступными. При зонной организации для каждой зоны задаются вместимость, указатель и правила отказа.
